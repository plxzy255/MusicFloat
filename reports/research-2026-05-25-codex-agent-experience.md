# Codex Agent Experience Audit - 2026-05-25

## Summary

MusicFloat already has better-than-usual agent guidance: `AGENTS.md`, a profiling contract, a performance-profiler spec, a build/run script, a self-release script, performance reports, and living lyrics/translation reports. The next improvements should make the common agent paths harder to miss: one full check command, more Codex actions, a doctor command, stricter profiling comparisons, and a report index that tells agents what to update after each kind of work.

## Gaps And Recommendations

### AGENT-001: Add more Codex actions

Follow-up status: closed through
`script/generate_codex_environment.sh`.

Evidence:

- `.codex/environments/environment.toml` now includes generated actions for:
  Run, Verify App, Test, Agent Verify, Doctor, Profile Report, Profile Disk,
  and Release Status.

Recommended maintenance:

- Do not manually edit `.codex/environments/environment.toml`; regenerate it
  with `./script/generate_codex_environment.sh`.
- Keep destructive actions such as profile clean, release install, and
  `--drive-music` profiling out of one-click defaults.

Why it helps:

- Agents will choose the right gate from the UI instead of re-discovering commands.
- The user can run repeatable checks without remembering script flags.

### AGENT-002: Add a single full agent check command

Evidence:

- `build_and_run.sh --verify` does not run tests.
- The profiler contract separately requires Xcode tests before performance comparisons.
- Agents can easily stop after "it builds and launches" even when test coverage is relevant.

Recommended command shape:

- Future `script/agent_verify.sh` or `script/check.sh`.
- Should run:
  - build and app verify,
  - all tests,
  - optional warning scrape,
  - `profile.sh report`,
  - `profile.sh disk`.
- It should be read-mostly and should clearly say which steps launched the app.

Why it helps:

- One command becomes the default handoff gate.
- It reduces inconsistent "verified" claims.

### AGENT-003: Add `profile.sh doctor`

Evidence:

- `xcrun xctrace list templates` can fail in sandboxed Codex contexts because Instruments wants to write under user cache locations.
- Live profiling depends on Music.app state, Xcode path, `mcpbridge`, disk headroom, and permission context.

Recommended doctor checks:

- Xcode path and version.
- `xcrun xctrace list templates` availability and cache-access warning.
- `mcpbridge` availability if needed.
- `.codex/traces` and DerivedData size.
- Music.app running/playing state for live preflight.
- Bundle ID and installed/running MusicFloat state.
- Current git branch and dirty state.
- Whether the command is read-only or mutating.

Why it helps:

- Agents can tell the difference between "profile command failed" and "sandbox/cache approval needed."
- The user gets safe diagnosis before a profiler run mutates active Music playback.

Follow-up status:

- Implemented as `./script/profile.sh doctor`.
- The command is intentionally read-only. In sandboxed Codex contexts it reports
  unavailable `xctrace` template access or process-list access instead of
  failing the whole doctor check.

### AGENT-004: Add strict profiling/report modes

Evidence:

- `profile.sh compare-runs` warns on mixed mode/scenario/invalid evidence, but can still exit successfully.
- `profile.sh report` is useful, but does not expose enough filters for larger ledgers.

Recommended options:

- `profile.sh report --json`.
- `profile.sh report --all`.
- `profile.sh report --mode live|demo|idle`.
- `profile.sh report --scenario NAME`.
- `profile.sh report --valid-only`.
- `profile.sh compare-runs --strict` that exits nonzero on mixed/invalid comparisons.

Why it helps:

- Agents can make report claims from structured data instead of copying terminal summaries.
- CI or pre-PR workflows can reject invalid performance comparisons.

### AGENT-005: Store privacy-safe live verification summaries in the ledger

Evidence:

- Live verification currently proves events by searching logs.
- The ledger stores artifact paths and run metadata, but not enough structured live outcome.

Recommended ledger fields:

- provider source,
- timed document yes/no,
- line count,
- syllable count,
- translation state,
- overlay appeared,
- live bridge primed,
- seek observed,
- track change observed,
- fallback source used,
- raw-log path.

Privacy rule:

- Do not store raw title, artist, album, or lyric lines in the ledger.

Why it helps:

- Future agents can summarize live outcomes quickly and safely.
- Reports can cite run IDs without re-reading raw logs unless needed.

### AGENT-006: Add a report index and update rules

Evidence:

- `reports/performance-flaws.md` has clear update expectations.
- `reports/bugs-and-issues.md`, `reports/lyrics-accuracy-status.md`, and `reports/translation-architecture-plan.md` are useful but less discoverable as a system.

Recommended `reports/README.md` or `reports/report-index.md`:

- Performance changes -> update `performance-flaws.md` when evidence opens/closes/invalidates a flaw.
- Lyrics pipeline changes -> update `lyrics-accuracy-status.md`.
- Translation architecture/runtime changes -> update `translation-architecture-plan.md`.
- Runtime bugs/timeouts -> update `bugs-and-issues.md`.
- Research-only passes -> add dated `research-YYYY-MM-DD-*` reports.

Why it helps:

- Agents know where durable knowledge belongs.
- The repo avoids stale "living trackers."

### AGENT-007: Add focused future agent specs

Existing:

- `.codex/agents/performance-profiler.md` is useful and should remain canonical for performance work.

Recommended future specs:

- `native-ui-auditor.md`
  - Reviews AppKit/SwiftUI ownership, panel/menu behavior, accessibility labels, keyboard/focus behavior, and screenshots.

- `lyrics-pipeline-forensics.md`
  - Owns provider order, catalog ID resolution, storefront/language issues, AX fallback, LRCLIB calibration, and live log evidence.

- `privacy-entitlements-reviewer.md`
  - Checks logs, usage strings, entitlements, sandbox, hardened runtime, Apple Events, Accessibility prompts, and token storage.

- `release-identity-doctor.md`
  - Checks bundle ID, version/build, `LSUIElement`, signing, entitlements, installed copy, and running process identity.

Why it helps:

- MusicFloat has several specialized risk zones.
- Separate specs keep future agents from mixing "performance", "lyrics correctness", and "distribution privacy" into one fuzzy review.

### AGENT-008: Add a warning stability check

Evidence:

- During this research pass, Xcode/agent observations saw unsafe strict-memory-safety warnings around Accessibility/event-listener helpers.
- Later build/test state did not keep surfacing them consistently.

Recommended command:

- Add a warning scrape to the future full check command.
- It should distinguish:
  - current compiler warnings,
  - stale Xcode navigator issues,
  - warnings from a previous build.

Why it helps:

- Agents will not over-report stale Xcode UI issues or miss real strict-memory-safety warnings.

## Recommended Agent Workflow

For normal code changes:

1. Read `AGENTS.md`.
2. Check current branch and dirty state.
3. Use Xcode MCP `BuildProject` when available.
4. Run all tests through Xcode MCP or the canonical test command.
5. Run `./script/build_and_run.sh --verify` for app-level smoke.
6. Update the relevant report if the change touches a living tracker.

For performance work:

1. Read `.codex/PROFILING.md`.
2. Read `.codex/agents/performance-profiler.md`.
3. Run `./script/profile.sh report`.
4. Run `./script/profile.sh disk`.
5. Use same-mode baseline/candidate comparison.
6. Update `reports/performance-flaws.md` only when evidence proves, invalidates, or closes a flaw.

For live Apple Music lyrics work:

1. Treat build/tests as necessary but not sufficient.
2. Use live `cv.MusicFloat` logs.
3. Verify provider source, timed document, line/syllable counts, and stale-result behavior.
4. Avoid exposing raw listening data in reports/PRs.
5. Update `reports/lyrics-accuracy-status.md`.

For translation work:

1. Decide if Translation is build-linked by default.
2. Measure memory before/after enabling Translation.
3. Keep source/target states explicit.
4. Update `reports/translation-architecture-plan.md`.

For distribution/security work:

1. Check sandbox, hardened runtime, entitlements, usage strings, and signing.
2. Explain Apple Events and Accessibility choices.
3. Avoid broad permissions unless a specific integration proves the need.
